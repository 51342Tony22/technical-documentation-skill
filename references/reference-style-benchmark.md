# 专利与软著写作边界基准

本基准根据本项目收到的五份专利材料（模块化太空超算平台、任务硬路由专家超分辨率效用预测、大幅面遥感影像任务感知解译、单粒子故障注入平台、计算机类自动保存系统）以及软著材料（多媒体摄像头服务系统、卫星轨道数据生成与查询系统、标准版模板）提炼。它是写作边界和表达风格的参考，不是事实来源；样例中的名称、参数、作者、代码和图片不得复制到新案件。

## 一、模式路由

| 路由信号 | 专利模式 | 软著模式 |
| --- | --- | --- |
| 文档对象 | 技术交底书 | 登记信息、操作说明书、详细设计说明书、源代码 |
| 高权重词 | 发明名称、背景技术、现有技术缺陷、技术问题、技术方案、发明形成过程、关键点、技术效果、实施例、附图、优选地、所述 | 软件全称、版本号、著作权人、开发环境、运行环境、功能、操作流程、模块、接口、输入项、输出项、异常处理、源程序量 |
| 典型动作 | 接收、采集、编码、计算、判断、路由、校验、锁紧、重构、生成、输出、发布 | 安装、启动、登录、输入、选择、点击、查询、保存、导入、导出、显示、退出 |
| 禁止混入 | 把页面操作、截图说明、代码行数当成发明技术特征 | 把新颖性、创造性、权利要求、现有技术对比当成软著主体内容 |

显式模式字段优先于关键词猜测。模式不明确且输入同时包含两类信号时，先询问模式，不加载两套 Prompt。

## 二、专利内容骨架

专利样例的共同结构是“技术背景与近邻方案评价 -> 与本发明对应的缺陷 -> 技术方案 -> 本发明创造的优点 -> 具体实施方式和附图”。写作结构按专利对象选择，不把所有案件强制写成同一种长文。其中：

1. 背景技术先交代宏观应用场景，再收敛到最接近的技术路线；每个缺陷都应能在后文找到对应改进点。
2. 背景支持两种组织方式。证据充分时优先采用“技术背景 -> 最接近的现有技术 -> 现有技术的缺陷和不足”三段式；模板另有要求或近邻路线不清晰时，可采用“现状描述与评价 -> 问题和缺点”的整合式。发明形成过程不是默认必写项，只有存在研发证据时才说明工程触发、技术难点、方案取舍和选择原因。
3. 技术方案必须落到技术特征：设备类写部件、连接、位置、配合和工作原理；方法类写输入、处理、条件、分支、输出和异常路径；算法类写特征、张量或数据结构、计算关系、损失/规则和参数来源。
4. “所述”“其中”“在一个实施例中”“优选地”用于连接已确认的技术关系或可选实现，不得用来掩盖空泛描述。优选参数必须注明来源、适用条件和是否为必要限定。
5. 技术方案支持三种组织方式。平台、装置和系统类优先采用“总体技术方案 + 部件/模块/连接/工作原理”的普通专利陈述；顺序处理本身构成核心的方法类采用 `S1-Sn`；同时包含结构关系与有序算法流程的采用混合式。`S1-Sn` 不是完整度指标。
6. “本发明创造的优点”独立成章，以“第一、第二、第三、第四……”逐项列出，每项采用“特征 -> 作用机制 -> 技术效果”的因果链，彼此不重复。不能只写“提高效率、降低成本、方便使用”；没有实测证据时使用定性表述，不虚构数值。
7. 具体实施方式可包含多个实施例；步骤编号只服务于真实技术流程，按技术复杂度自适应，不要求固定到 `S24`。启动演示、截图、哈希和预检属于证据流程，不自动成为发明步骤。
8. 附图是技术关系的表达，不是装饰。专利关键结构优先使用代码或结构化蓝图确定性绘图；真实界面截图只能证明可见运行状态，不能替代结构图、流程图或算法图。
9. 工程实现、接口契约、代码哈希和运行预检不是专利交底书的默认章节。只有用户明确要求接口/API/代码/运行证据，或模板明确要求时，才启用工程实现证据路线；已有代码或截图仍可作为内部事实依据和附图来源，但不自动改变正文风格。
10. 输入含有可追溯的实验组、测量值、对比结果、消融结果、时间序列或参数响应数据时，实验结果表和数据图具有较高正文优先级：表格保留精确值，图形揭示趋势、差异、分布或交互。量化图默认使用 Altair；架构图、流程图等结构图仍使用确定性结构绘图。没有实验数据时不得为丰富版面而虚构表格或曲线。

## 三、软著内容骨架

软著样例把材料分成不同读者和任务，不能合并成一篇“专利式”长文：

1. 登记信息采集表只填权利登记事实、软件身份、开发/运行环境、语言、源程序量、开发目的、行业和功能技术特点；不在这里展开现有技术检索。
2. 操作说明书面向使用者，写前置条件、启动/登录、页面导航、输入动作、主要功能的连续操作和预期结果。用“点击、输入、选择、查询、保存、显示”等可复现动作词，每个主要界面配完整截图和相邻说明。
3. 详细设计说明书面向开发人员或技术审核人员，写总体架构、模块职责和依赖、数据结构、接口、算法、运行流程、异常处理和限制。每个模块宜按“程序描述、功能、输入项、输出项、算法/流程、异常或限制”展开；只有有证据时才写性能指标。
4. 源代码文档只放项目自有代码，保持真实文件边界、开头/结尾和确定的选取顺序；项目合格总行数和实际提交行数分开记录，禁止复制模板代码或补行。
5. 软著材料使用“本软件、本系统、该模块、用户、程序、接口”等表达，不使用“本发明、发明目的、现有技术缺陷、创造性、权利要求”等专利套话。可以写“技术特点”，但应描述实现特点而不是论证专利性。
6. 有界面的应用软件仍要求操作说明书和详细设计说明书分别交付；操作说明书解释“怎么用”，详细设计说明书解释“怎么实现”，截图可以在两者中被不同角度引用，但正文不能互相替代。

## 四、截图与图像边界

- 软著操作说明书和专利运行证据都只能使用真实软件截图。
- 主界面截图必须包含整个操作界面；如软件运行在浏览器中，默认包含浏览器边框或在证据说明中明确截图范围。
- 截图主体必须完整、居中、可读、无遮挡、无滚动容器或边缘截断；图中声明的按钮、节点、连线、标签、版本和结果必须全部可见。
- 页面放不下时改变运行时视口或提供真实的证据布局后重新截图，不能靠后期裁剪、拼接、补绘或生图修复。
- 生图只能用于明确标注的概念插图，不能冒充界面、实验曲线、日志、波形、测量结果或专利关键结构。

## 五、最小风格检查

生成前检查：模式是否明确、文档读者是否明确、内容是否落在该模式的章节中、关键词是否属于该模式、是否误用了另一模式的禁用词。

生成后检查：专利是否存在“缺陷—技术特征—技术效果”对应链，软著四份材料是否身份一致且职责分离，截图是否完整居中，代码/截图/参数是否均有证据来源。
